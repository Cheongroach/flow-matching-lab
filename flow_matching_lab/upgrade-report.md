# 这个项目是什么水平，下一步难在哪里

目前更适合称为“扎实的大作业 / 入门研究复现”。它包含真实训练、模型对照、结果记录和交互，不只是播放一个动画；但任务仍是很小的手写数字，没有大型生成模型或生产服务的验证。

Flow Matching 是主流方法，使用主流方法不等于项目已经达到主流系统水平。下面的分档是工程判断，不是学术榜单认证。

## 它已经做到什么

原始版本从随机噪声生成 14×14 数字，可以修改噪声看结果变化。新版把图像提高到 28×28，并让模型接收已知笔画，补完剩下的部分。

![改变观察笔画，补全结果也改变](docs/images/edit-response-friendly.png)

这更接近“我改输入，输出跟着变”的需求。程序负责保留已知像素，网络负责生成未知像素；这两项能力需要分别验证。

我们比较了同分辨率的 MLP 和 U-Net。MLP 把像素摊平处理；U-Net 利用图像空间关系。它们使用同一类 Flow Matching 训练目标、相同数据和更新次数，但参数量、计算量不同，且没有分别充分调参。

| 已完成的比较 | 观察到的结果 | 能说明什么 |
|---|---|---|
| 32 步普通类别生成 | 加宽 MLP 类别一致率 70.70%；U-Net 两次训练均值 89.35% ± 0.49 个百分点 | 当前设置下，U-Net 更符合请求类别 |
| 特征分布比较 | 加宽 MLP 距离 289.15；U-Net 14.36 ± 0.88 | 用本实验识别器衡量，生成分布更接近真实参考；不是论文 FID |
| 给真实左半图补右半图 | U-Net 未知区域误差 0.2292；先生成再粘贴是 0.3057 | 当前测试条件下，相对误差下降约 25% |
| 加宽 MLP 的同一补全比较 | 误差 0.5701；粘贴对照 0.4351 | 反而恶化约 31%，失败结果同样保留 |

U-Net 有 236,545 个参数，加宽 MLP 有 9,674,256 个，约为前者的 40.9 倍。参数更少不保证运行更快；共享 CPU 训练记录中 U-Net 耗时更长，这也不是严格性能基准。

误差和距离没有“画对的百分比”含义。计算口径、样本数量和局限放在 [实验解读](improved/results-friendly.md)，全部数值放在 [完整表格](improved/results.md)。

## 为什么评为大作业

| 层级 | 需要具备什么 | 当前状况 |
|---|---|---|
| 小玩具 | 能展示一个效果，实验规模和验证有限 | 原始交互的应用范围接近这一档 |
| 大作业 | 真实训练、可重复评估、对照、错误处理和明确局限 | 当前达到 |
| 一般工程或研究项目 | 更真实的任务、充分对照与调参、可靠运行和标准评估 | 还缺这些证据 |
| 主流系统 | 接入成熟模型生态，质量、控制、成本和运维有竞争力 | 尚未验证 |
| SOTA | 在明确任务和公平预算下超过强基线，贡献新且可复现 | 没有这样的实验 |

原始版本也有三次独立训练、解析验证和官方路径校验。因此“偏玩具”主要指它的任务范围，而非否认已经做过的工程工作。

新版通过 11 项 CPU 检查，真实 HTTP 请求还验证了重复输入结果一致、输入变化、已知区域保留、非法请求拒绝和保存回读。浏览器在此环境打开页面时退出，画笔、上传和移动布局的操作自动化未通过；也没有 GPU 服务性能数据。

## 再往上做，先遇到的是输入问题

目前模型训练时看到的是半图和矩形遮挡。用户画两笔稀疏草图、写一个很歪的数字，甚至上传照片，都会与训练输入不同。把网络加大，不会自动解决这类差异。

想提升交互实用性，需要用相应输入训练：不同人的字迹、稀疏笔画、不同形状遮挡，并按输入类型分别评估。也可以逐步扩展字母、衣物或彩色小图，但不能把 MNIST 上的结果直接搬过去。

## 第二个难点是“更好”怎样判断

高识别分数可能来自几乎相同的标准写法。新版一步类别一致率约 99.65%，同类像素变化却只有真实数据约 2.4%。补全的平均绝对误差也可能偏向平均结果，而惩罚另一种合理写法。

后续需要固定样例、多个生成结果、笔画边界连续性和独立人工评价。对照也应更充分：移除已知图像输入、改变网络、改变生成与补全训练比例，分别检查结果。这种“每次只改一个因素”的实验通常叫消融。

训练种子要增加，参数与计算预算要交代清楚。只有一个加宽 MLP 和两个 U-Net，足够报告当前观察，不足以建立广泛架构结论。

## 第三个难点是减少生成成本

生成走 N 次 Euler，要调用速度预测 N 次。Heun 每步调用两次。加强 CFG 时又要有类别、无类别两条网络分支，因此减少步数和合并计算很有吸引力，但一步结果的变化不足说明：不能只追求速度。

研究上可以尝试更好的时间抽样、OT 配对、reflow 或蒸馏。OT 配对在训练批内选择更合适的噪声与图像对应；reflow 用现有模型生成的新端点配对继续训练；蒸馏让少步模型学习多步教师。它们都有额外训练成本，也可能继承错误或减少多样性，本项目尚未实现。

高分辨率还会放大计算。256×256 的像素数约是 28×28 的 83.6 倍，网络往往也更深、更宽。成熟系统常先把图片压缩为潜在表示（latent），在这个空间生成，再通过解码器还原。常见的 VAE 就是这类编码、解码组件；代价是压缩可能丢掉细节。Transformer 的注意力成本还取决于图像被切成多少块，而不能对所有架构简单套用像素数量的平方。

## 对 AI Infra 方向，更值得做哪一步

可以选择规模适中的预训练 FM 或 rectified-flow 模型，在真实 GPU 上做交互服务。这样不必先承担从零训练大型模型的成本，又能研究真实的推理调度问题。

先固定模型、图像大小、输入遮挡、随机噪声和最低质量要求。分别测量网络计算、排队、编码解码、数据传输耗时，建立基线，再尝试低精度计算、编译、CFG 分支合批、多个请求一起计算和取消过时输入。

例如，用户连续画十笔，旧请求仍在生成就可能拖慢最新一笔。需要保证新输入优先，旧输出不覆盖新输入；不同步数的请求也可能让一个批次互相等待。

| 要报告的指标 | 它回答的问题 |
|---|---|
| P50 / P95 延迟 | 一半 / 95% 的请求在多长时间内完成 |
| 有效 images/s | 每秒完成多少符合要求、没有过时的结果 |
| 峰值显存、GPU 利用率 | 资源花在哪里，是否有瓶颈 |
| 失败率、每张有效结果成本 | 优化是否可靠、是否实际省钱 |

这样的系统结果更能体现 AI Infra 能力。当前简历可以写已经验证的图像条件训练、约 25% 补全误差改善和请求验证；在 GPU 实测前，不写推理加速倍数、生产吞吐或 SOTA。

## 技术与数据入口

`image_model.py` 实现图像条件网络和已知区域约束；`image_train.py` 负责训练和恢复；`image_eval.py` 评估；`draw.py` 与 `editor.html` 是交互服务。更完整的原理见 [一步步认识 Flow Matching](research-report-friendly.md)。

方法来源：[Flow Matching](https://arxiv.org/abs/2210.02747)、[官方 Guide 与代码](https://arxiv.org/abs/2412.06264)、[OT-CFM](https://arxiv.org/abs/2302.00482)、[高分辨率 Rectified Flow Transformer](https://arxiv.org/abs/2403.03206)。这些是后续方向的资料，本项目没有复现其中的大型系统。
